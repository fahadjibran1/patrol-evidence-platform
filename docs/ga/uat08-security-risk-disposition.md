# GA-UAT-08 Windows desktop security disposition (internal)

Status: **PROPOSED RELEASE-RISK DISPOSITION — NOT A GA APPROVAL**. Assessed 20 September 2026 from source baseline `3742c868819720564ed8f3fa7a720d8e20f24d22`, the source lockfile after the narrowly scoped `ws` patch, and the **previous, unchanged** signed v1.0.2 `resources/app` payload. No new desktop payload or installer was built in GA-UAT-08. An operator must approve any temporary residual-risk acceptance. This is not external security certification.

## Audit scope and release gate

`npm audit --omit=dev --json` covers the root and npm workspaces, including the separate licence API. It reported **1 critical, 14 high, 14 moderate, 1 low** before this patch and **1 critical, 13 high, 14 moderate, 1 low** after the source-lock patch. The removed high is `ws`/`GHSA-96hv-2xvq-fx4p`. This audit is neither a Windows payload inventory nor proof that a reported operation is exploitable. The earlier package inspection is recorded in [GA-UAT-07 triage](uat07-production-dependency-security-triage.md).

The previous signed Windows payload still contains `ws@8.20.1`. The source lockfile now resolves `ws@8.21.3` for Puppeteer-core (compatible with its `^8.19.0` range), and the local source test resolves and loads that version. **Before any GA candidate can be approved, a newly authorised package build must demonstrate that `resources/app` contains `ws@8.21.3` with no runtime-loaded vulnerable duplicate, followed by the packaged WhatsApp/Edge and security regression.** Do not treat the source audit as that verification. The old signed RC, manifest, release inventory and public v1.0.1 remain unchanged.

At the audit package-record level, the **old actual Windows payload** has 11 shipped high records (`ws`, the five-package `extract-zip` chain, and five other shipped packages); no critical record is shipped. The **projected patched payload** would have 10 shipped high records if it matches the source lock exactly. This is a projected count, **not an inventory of an existing new package**. The repository audit's other three high records and one critical record are outside the desktop payload.

Release policy: assess actual shipped versions, whether the vulnerable operation is loaded and reached, attacker influence, controls and safe fixes. A shipped, attacker-influenced, reachable high/critical issue with a safe fix is **REMEDIATE BEFORE GA**. An inherited audit finding is not a second independent exploit primitive. No finding below is dismissed as a false positive.

### `extract-zip` boundary in detail

Installed Edge is selected as a local executable by `src/collectors/whatsapp-web-runtime.config.ts` and passed into the `whatsapp-web.js` `LocalAuth` client in `src/collectors/whatsapp-helper.main.ts`. Puppeteer controls that already installed browser; it is **not** fetching/extracting a browser archive in this flow. The packaged `@puppeteer/browsers` browser-install implementation is present only as a dependency. A normal customer can initiate WhatsApp connection and mapping, not a browser-download/ZIP-extraction command. A WhatsApp image/media download follows evidence ingestion, not `@puppeteer/browsers` archive installation. A hostile web page could compromise a browser by a different flaw, but merely being opened in Edge does not establish an input path into Node's `extract-zip`. These conclusions must be revalidated after changes to browser provisioning or Puppeteer/WhatsApp versions.

The audit metadata offers `whatsapp-web.js@1.34.2` as a “fix” for this inherited chain. That is a **downgrade** from the certified `1.34.7`, not a compatible patched `extract-zip` release. It is not an approved remediation and would itself require WhatsApp/Edge recertification. The two upstream [`extract-zip` advisories](https://github.com/advisories/GHSA-jmr9-qjv8-65gv) [list no patched version](https://github.com/advisories/GHSA-7pqw-9j4j-h8q3); the [ws advisory](https://github.com/advisories/GHSA-96hv-2xvq-fx4p) identifies `8.21.0` as the patched floor, and the [ws release history](https://github.com/websockets/ws/releases) shows subsequent fragment-limit hardening included in selected `8.21.3`.

## Follow-up and immutable release evidence

1. **Desktop build gate:** authorise a fresh unsigned package, enumerate all package/version instances under its actual `resources/app`, and prove patched `ws` is the only runtime-loaded WebSocket transport. Verify the source lock and actual package agree. Do not overwrite the previous signed RC.
2. **Functional gate:** run packaged clean first run, dirty upgrade, dynamic backend/helper endpoint, production three listeners, WhatsApp/installed-Edge LocalAuth, reconnect/relink, mapping, licence, evidence, backup and process cleanup. Then independently review any new signed candidate. Source/Jest tests do not replace this gate.
3. **Residual risk gate:** obtain explicit Vesoft release-authority acceptance for each proposed `ACCEPT TEMPORARY RESIDUAL RISK` row, with a review date and owner. If actual runtime testing finds customer/attacker input reaches any vulnerable operation, change that row to **REMEDIATE BEFORE GA** or **BLOCKING — REQUIRES DESIGN CHANGE**.
4. **Open-source gate:** the only source-lock delta in this task is `ws 8.20.1 → 8.21.3`. Its MIT licence and licence-text hash are unchanged. No LGPL component changed. After an authorised new package, regenerate the actual shipped dependency inventory and version-specific notice record. Do not reuse previous release hashes as proof of a new payload; reassess LGPL/source-package contents against that new inventory.

The prior signed RC still has its previous 403 shipped instances / 361 unique package-version records. The prospective source lock replacement should not change package *counts*, but that is only a prediction until a new payload is built and enumerated. No customer-facing security claim or external certification follows from this internal disposition.
